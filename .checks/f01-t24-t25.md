# F-01 T24/T25 Implementation Checks

**Binding sources:**
- `.specs/features/f-01-platform-provisioning/ui-spec.md` — unified Membros administration page.
- `.specs/features/f-01-platform-provisioning/invitation-onboarding-spec.md` — invite-scoped signup, universal email OTP, identity match, explicit acceptance.
- `.specs/features/f-01-platform-provisioning/design.md` and `tasks.md` — domain boundaries, acceptance rules, full gate.
- `AGENTS.md` — tenant isolation, official dependency docs, no secrets, PostgreSQL lifecycle.

**Profile:** light. UI and Auth contract/integration assertions are required; no fault injection is specified for this profile.

## Checks

**C1 — Unified members navigation.** The administration screen exposes one Membros tab and no separate Convites tab; the member invitation action stays on that screen.
Proof: `PlatformAdministrationViewIntegrationTests.membersAndInvitationsShareOneMembersTab`

**C2 — Combined records and filters.** The unified list can filter by tenant and status and represents active memberships plus pending/history invitations without rendering an accepted invitation as a duplicate member.
Proof: `PlatformAdministrationViewIntegrationTests.membersListCombinesMembershipsAndInvitationsWithTenantAndStatusFilters`

**C3 — Inline invitation lifecycle.** Creating an invitation in Membros leaves the user on the page, shows its pending state/link, and does not create an active membership.
Proof: `PlatformAdministrationViewIntegrationTests.invitingFromMembersKeepsPendingInvitationInline`

**C4 — Revocation safeguards.** Cancelling a revoke confirmation leaves the record unchanged; confirming invokes the existing revoke command and updates the view.
Proof: `PlatformAdministrationViewIntegrationTests.revocationRequiresConfirmationAndRefreshesMembersList`

**C5 — Invitation-scoped signup.** Signup is available only from a valid invitation, uses its normalized email as a read-only address, and sends only the public API key to the Supabase Auth API.
Proof: `InvitationOnboardingViewTests.signupIsInvitationScopedAndUsesInvitedEmail`
Proof: `InvitationOnboardingViewTests.signupRejectionKeepsExistingAccountLoginAvailableForTheInvitedEmail`
Proof: `InvitationOnboardingViewTests.resendWithoutConfirmedDeliveryKeepsExistingAccountLoginAvailable`
Proof: `InvitationOnboardingQueryServiceTests.onlyAValidPendingInvitationRevealsTheReadOnlyRecipientAddress`
Proof: `InvitationOnboardingQueryServiceTests.suspendedTenantInvitationDoesNotExposeAnAddressForSignup`
Proof: `InvitationOnboardingQueryServiceTests.expiredOrMissingInvitationDoesNotExposeAnAddressForSignup`
Proof: `SupabaseAuthClientTests.signsUpWithInvitationEmailUsingOnlyPublicApiKey`

**C6 — Universal OTP verification.** A not-yet-verified invitation recipient receives an email OTP; entering it verifies the same email and establishes the server-side Supabase session for the returned subject.
Proof: `SupabaseAuthClientTests.verifiesSignupEmailOtpAndReturnsVerifiedSession`
Proof: `SupabaseAuthClientTests.resendsOtpForAnExistingUnverifiedSignup`
Proof: `SupabaseInvitationAuthServiceTests.otpSessionRequiresVerifiedSupabaseProfileForTheInvitedEmail`
Proof: `SupabaseInvitationAuthServiceTests.otpSessionForAnotherEmailIsRejectedBeforeItCanBecomeApplicationAuthentication`
Proof: `InvitationOnboardingViewTests.otpVerificationContinuesWithVerifiedInviteIdentity`
Proof: `InvitationAcceptanceViewTests.unverifiedExistingAuthAccountMustCompleteOtpBeforeAcceptance`

**C7 — Owner/recipient account switching.** When the active session is another email (including the owner), onboarding lets the recipient switch accounts while preserving the same invitation; a wrong account cannot accept it.
Proof: `InvitationOnboardingViewTests.otherAuthenticatedAccountCanSwitchAndResumeSameInvitation`
Proof: `InvitationAcceptanceViewTests.mismatchedVerifiedIdentityCannotAcceptInvitation`

**C8 — Acceptance is the only membership activation.** Signup or OTP verification alone does not create local identity/membership; explicit acceptance activates membership only after verified email exactly matches the invitation.
Proof: `InvitationAcceptanceViewTests.openingInvitationOnlyShowsExplicitConfirmationAndDoesNotExposeToken`
Proof: `InvitationAcceptanceViewTests.acceptsOnlyAfterExplicitConfirmationUsingVerifiedMatchingSessionIdentity`
Proof: `PlatformProvisioningEndToEndIntegrationTests.publicOriginInvitationFlowCreatesLinkAndActivatesMembershipWithAudit`

## Swept

- authorization/tenant boundary: C1-C4 preserve platform-admin-only controls; C5-C8 never accept a client-supplied tenant or grant local membership at Auth signup.
- state transitions and audit: C3-C4 and C8; only explicit acceptance creates membership and acceptance audit.
- secrets and PII: C5-C6; no secret API key, password, OTP or raw invitation token in logs/audit.
- external dependency behavior: mocked Supabase Auth API; no real Auth account/email is created by automated tests.
- manual boundary: real SMTP delivery and published-browser UAT remain external T23 checks.
